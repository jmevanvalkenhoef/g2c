# Escrow Service Specification

Item-for-sats escrow over Bitcoin Lightning, coordinated against a third-party game API.
Companion doc: `DISCUSSION_SUMMARY.md` (rationale & decision log).

Status: DRAFT v0.1

---

## 1. Overview

The escrow service is a standalone process that:

1. Issues **hold invoices** to buyers for an item sale.
2. On HTLC lock: instructs the **game backend** to transfer item ownership (idempotent).
3. Pays the **seller** via an invoice resolved from their Lightning address.
4. Settles the hold invoice — completing the buyer's payment — only after 2 and 3
   are confirmed.
5. On any definitive failure before money moved: cancels the invoice (buyer is
   auto-refunded by Lightning's own timeout) and rolls back the transfer if needed.

Guarantee: **no state exists where sats moved and ownership didn't (or vice versa)**,
except recoverable windows documented in §7.

### Components

```
                ┌──────────────┐  HTTPS (HMAC)   ┌───────────────┐
                │ Game backend │◀───────────────▶│ Escrow service │
                │  (3rd party) │                  └───────┬───────┘
                │  items only  │                          │ gRPC (cln-grpc)
                └──────┬───────┘                  ┌───────▼───────┐
                       │ shows payment_request    │ Greenlight    │
                ┌──────▼───────┐  BOLT11          │ hosted CLN    │
                │ Buyer wallet │─────────────────▶│ (our keys)    │
                └──────────────┘                  └───────┬───────┘
                ┌──────────────┐  BOLT11                   │
                │ Seller wallet│◀──────────────────────────┘
                └──────────────┘
```

- **Game backend** (`api.game.example`): owned by third party. Item ownership, user IDs,
  seller Lightning addresses in user profiles. *Holds no sats.*
- **Escrow service** (this spec): Rust or Go or Python; single binary/process; local
  SQLite state store; the only Lightning participant.
- **Greenlight node**: hosted CLN, keys held by us (device credential in secret store).
- **Wallets**: buyer and seller use any wallet (custodial fine). They are never aware of
  the escrow machinery beyond paying a payment request / being paid.

### Explicit non-goals

- No user balance custody of any kind.
- No refunds-as-a-feature: cancellation of the hold invoice is the refund.
- No multi-item/multi-seller carts in v1 (one sale = one item = one hold invoice).
- No on-chain BTC, no other assets.

## 2. Primitives and budget

| Primitive | Source | Notes |
|---|---|---|
| Hold invoice (hash supplied by us, preimage generated by us) | **`BoltzExchange/hold`** CLN plugin on a self-run node — verified 2026-02-14, see `verification-greenlight-holdinvoices.md`. Greenlight: not possible (no plugin support). LND fallback: native `AddHoldInvoice` (requires handing node the preimage at creation — acceptable, weaker than hash-only) | **Milestone 0 outcome recorded; node-backend decision (A/B/C) pending** |
| Invoice status stream | CLN notifications / `listinvoices` polling | drives state machine |
| Seller payout resolution | **PayoutResolver** seam — `LnUrlResolver` (LUD-16) / `NwcResolver` (NWC `make_invoice` via kind 23194/23195) | fresh invoice minted at purchase time; core state machine is resolver-agnostic |
| Payment to seller | CLN `pay` (BOLT11 from PayoutResolver) | `listpays` for status |
| Local transactional state | SQLite WAL | single writer, `payment_hash` as PK |

**Hold window budget**: from HTLC lock to settle must stay well inside the final-hop
CLTV delta. Target: **≤ 10 s** p99 (game API call + invoice fetch + payment attempt).
Hard alarm at 30 s. Never perform human-in-the-loop actions while holding.

**Invoice expiry**: hold invoice `expiry = 600 s`. Reaper (§8) releases reservations.

**Units**: msat internally everywhere; convert only at edges.

**Fee**: spread. Hold invoice `amount_msat = X`; seller paid `X - fee_msat`.
`fee_msat` configured per sale (default from config, min/max clamps). Fee accrues in
our node's channel balance; periodic sweep/rebalancing is ops concern, out of scope.

## 3. APIs

### 3.1 Escrow API (we serve; called by game backend only, never by game clients)

Auth: HMAC-SHA256 over `(method, path, body, nonce)` with shared per-deployment secret.
Idempotent on `item_id + buyer_id` for in-flight sales (one open sale per item).

```
POST /v1/sales
  { "item_id": "...", "buyer_id": "...", "seller_id": "...",
    "amount_msat": 21000, "fee_msat": 100,
    "seller_payout": { "type": "lnurl", "target": "satoshi@wos.example" }
    // or: { "type": "nwc", "target": "nostr+walletconnect://…" }
    //    (make_invoice-only permission; the URI is a SECRET — encrypt at rest,
    //     never log. Game backend stores payout methods in seller profiles.)
  }
→ 201 { "sale_id": "uuid", "payment_request": "lnbc...",
        "payment_hash": "<hex>", "expires_at": "RFC3339" }

GET /v1/sales/{sale_id}
→ 200 { "state": "HTLC_HELD" | "COMPLETED" | "CANCELLED" | ...,
        "payment_hash": "...", "failure_reason": "..."? }
```

Optional webhook back to game backend on terminal states (separate shared secret).

Both payout types mean the same thing to the core: **a fresh invoice is minted at
purchase time; the seller is never involved at sale time.** Resolution goes through
the internal `PayoutResolver` seam (§2) so the state machine is resolver-agnostic.
Adapter-specific behavior is contained in the adapter: LNURL failures are fast and
unambiguous (HTTP); NWC relay timeouts are ambiguous (wallet offline vs slow) and use
their own deadline before being treated as row #5 failures.

### 3.2 Game API (they serve; called by us; contract to hand to the third party)

Auth: HMAC as above. All mutations keyed by `idempotency_key = payment_hash`
(hex). **Contractual requirements:** mutations must be atomic server-side (single SQL
transaction: item transfer + any internal accounting) and replay-safe.

```
POST /execute_sale
  { "item_id": "...", "buyer_id": "...", "seller_id": "...",
    "idempotency_key": "<payment_hash>" }
→ 200 { "status": "done" }        # or "already_done" — both mean confirmed
→ 409 { "status": "rejected", "reason": "item_unavailable" }   # definitive
→ 5xx / timeout                   # AMBIGUOUS → must retry / reconcile via status

GET /sale_status?key=<payment_hash>
→ 200 { "status": "done" | "not_found" }

POST /rollback_sale
  { "idempotency_key": "<payment_hash>", "reason": "seller_payment_failed" }
→ 200 { "status": "rolled_back" } | 409 { "status": "already_rolled_back" }
```

### 3.3 Node backend integration — Greenlight ruled out (2026-02-14)

Greenlight cannot load custom plugins (open brainstorm issue #423, "TBD", since
2024-05) and core CLN has no native hold RPCs — so Greenlight offers no path to hold
invoices. Evidence: `verification-greenlight-holdinvoices.md`.

Node backend options:

- **A (recommended): self-run CLN on VPS + `BoltzExchange/hold`** — plugin exposes
  `holdinvoice/settleholdinvoice/cancelholdinvoice/injectinvoice` + gRPC streaming,
  release binaries available; hash-only creation preserves the strong guarantee
  (even the node can't settle without our preimage).
- **B: self-run LND (+neutrino) or LND hoster** — native hold RPCs, spec primitives
  map 1:1; preimage must be supplied at creation.
- **C: ask Blockstream to whitelist the plugin** — pursue in parallel, non-blocking.

Common requirements regardless of option:

- cln-grpc / LND gRPC; node reachable while any sale is in a non-terminal state.
- Notification subscription for invoice state changes (poll as fallback at 1–5 s
  while waiting states exist).
- Credentials (node admin / plugin client certs) from secret manager; never on disk
  in repo.

## 4. Sale state machine

```
CREATED ──▶ AWAITING_PAYMENT ──▶ HTLC_HELD ──▶ EXECUTING ──▶ PAYING_SELLER ──▶ SETTLING ──▶ COMPLETED
   │              │                  │             │              │                │
   │              │ (expiry)         │ (transfer   │ (pay fails)  │ (settle fails) │
   │              ▼                  │  rejected)  ▼              ▼ (retry)       ▼
   └────────▶ CANCELLED ◀────────────┘        ROLLING_BACK ──▶ CANCELLING   (terminal)
                     ▲                        (rollback_sale
                     └────────────────────────+ cancel invoice)
```

State semantics (persisted in SQLite, one row per sale, transitions single-threaded per
sale via `UPDATE ... WHERE state = ?` optimistic lock):

| State | Meaning | Money moved? |
|---|---|---|
| CREATED | sale accepted, preimage generated, invoice not yet issued | no |
| AWAITING_PAYMENT | hold invoice live, payment request returned to game | no |
| HTLC_HELD | buyer's HTLC locked at node (fully funded incl. MPP parts) | no (in-flight) |
| EXECUTING | calling `execute_sale` (retries allowed) | no |
| PAYING_SELLER | resolving LN address → invoice → `pay` (retries w/ fresh invoices) | no (until success) |
| SETTLING | releasing preimage to settle hold invoice | — |
| ROLLING_BACK | transfer confirmed done but seller payment definitively failed; calling `rollback_sale` then cancel | no |
| CANCELLING / CANCELLED | cancel invoice; buyer auto-refunded by protocol | no |
| COMPLETED | transfer done, seller paid, hold invoice settled | yes (all) |

Invariant: **preimage released ⇔ (`execute_sale` confirmed done AND seller payment
confirmed succeeded)**. Enforced by the state machine; no other code path may settle.

## 5. Purchase flow (happy path)

```
Game          Escrow                    CLN/Greenlight      Seller wallet
 │ create_sale │                            │                    │
 │────────────▶│ gen preimage+hash          │                    │
 │             │── holdinvoice(hash,X) ────▶│                    │
 │◀─ pay_req ──│                            │                    │
 │ (show to buyer)                          │                    │
 │             │◀─ HTLC locked (event) ─────│                    │
 │             │ state=EXECUTING            │                    │
 │ execute_sale│                            │                    │
 │────────────▶│ (retry until 200/409)      │                    │
 │◀─ done ─────│                            │                    │
 │             │ state=PAYING_SELLER        │                    │
 │             │ resolve LN addr → invoice  │                    │
 │             │── pay(X-fee) ─────────────▶│───────────────────▶│
 │             │◀─ pay success (preimage') ─│                    │
 │             │ state=SETTLING             │                    │
 │             │── settle(preimage) ───────▶│ buyer's pay completes
 │             │ state=COMPLETED            │                    │
```

## 6. Failure matrix

| # | Failure | Detection | Action | End state | Sats risk |
|---|---|---|---|---|---|
| 1 | Buyer never pays | invoice expiry / reaper | release item reservation | CANCELLED | none |
| 2 | Buyer pays partially (MPP incomplete) | invoice not fully funded | wait; expiry cancels | CANCELLED | none |
| 3 | `execute_sale` definitive 409 | response | cancel invoice | CANCELLED | none |
| 4 | `execute_sale` timeout/5xx | response/timeout | retry; then `sale_status`; only 200/409 proceeds | EXECUTING → … | none |
| 5 | Seller payout resolution fails (LNURL: HTTP error, unambiguous. NWC: relay timeout, ambiguous — adapter deadline applies) | resolver result | retry with backoff (LNURL: same endpoint; NWC: re-request); give up → rollback + cancel | ROLLING_BACK → CANCELLED | none |
| 6 | Seller payment routing fails | `pay` failed status | re-resolve fresh invoice (PayoutResolver), retry N; then rollback + cancel | ROLLING_BACK → CANCELLED | none |
| 7 | Seller payment succeeded, settle fails | local error | retry settle forever (we hold preimage; HTLC is ours) | SETTLING → COMPLETED | none (worst case: HTLC timeout refunds buyer while seller paid → **fee+principal loss; alert + manual reconcile**) |
| 8 | Crash anywhere | restart | §8 reconciliation | — | none beyond #7 window |
| 9 | Item re-listed/raced (reserved but seller changed mind) | `execute_sale` 409 | cancel | CANCELLED | none |

Notes:
- #7 is the only principal-risk window and it is local-operation-sized (seconds), plus
  requires simultaneous failure. Alert immediately on any sale sitting in SETTLING > 5 s.
- After seller payment succeeds, **never** roll back; only settle (else we'd have paid
  the seller without collecting from the buyer).

## 7. Trust & atomicity statement (for the third party)

The only cross-system commit points are (a) `execute_sale` confirmation and (b) seller
payment success. Both precede preimage release. The game API's idempotency on
`payment_hash` is what makes retries safe; without it the design is void.

---

## 8. Crash recovery & reconciliation

On startup and every 30 s:

1. Load all sales in non-terminal states.
2. Query CLN: `listinvoices` (our hold invoice state), `listpays` (seller payment
   status).
3. Query game: `sale_status` for sales past EXECUTING.
4. Drive the state machine forward per §4 invariants; all actions idempotent
   (`payment_hash` keys everywhere).
5. Never guess ambiguous outcomes: if `sale_status` = not_found and no definitive 409
   was recorded, keep retrying `execute_sale` (do not cancel; buyer is still holding
   the HTLC which times out safely on its own).

Reaper: sales in AWAITING_PAYMENT past `expires_at + 60 s` → cancel invoice, CANCELLED.

## 9. Local store (SQLite)

```sql
CREATE TABLE sales (
  sale_id          TEXT PRIMARY KEY,           -- uuid
  payment_hash     TEXT NOT NULL UNIQUE,       -- hex, idempotency key everywhere
  preimage_enc     BLOB NOT NULL,              -- encrypted at rest
  item_id          TEXT NOT NULL,
  buyer_id         TEXT NOT NULL,
  seller_id        TEXT NOT NULL,
  seller_payout_type TEXT NOT NULL,         -- 'lnurl' | 'nwc'
  seller_payout_uri  TEXT NOT NULL,          -- address, or ENCRYPTED NWC URI (secret!)
  amount_msat      INTEGER NOT NULL,
  fee_msat         INTEGER NOT NULL,
  state            TEXT NOT NULL,
  failure_reason   TEXT,
  hold_invoice_id  TEXT,                       -- CLN label
  seller_pay_id    TEXT,                       -- CLN payment id
  attempts         INTEGER NOT NULL DEFAULT 0,
  created_at       TEXT NOT NULL,
  updated_at       TEXT NOT NULL
);
CREATE INDEX idx_sales_state ON sales(state);
CREATE TABLE state_log (       -- append-only audit trail
  payment_hash TEXT, from_state TEXT, to_state TEXT, detail TEXT, ts TEXT
);
```

## 10. Security

- Escrow API & Game API: HMAC-SHA256, nonce + timestamp window (±30 s), constant-time
  compare.
- Preimages encrypted at rest (AES-GCM, key from secret manager / env).
- Greenlight device credential in secret manager; no macaroons on disk.
- The escrow process holds power equivalent to "transfer items without payment" toward
  the game — treat the HMAC link as production-critical, rotate secrets, IP allowlist.
- Logs: never log full preimage or payment_request beyond operational need; hash-prefix
  correlation IDs instead.

## 11. Observability

Metrics (Prometheus): sales by state, hold-window duration histogram, game API
latency/error rate, seller payment failure rate, count in SETTLING (must be ~0),
count in ROLLING_BACK, fee earned (msat).

Alerts: any sale in SETTLING > 5 s; any sale in HTLC_HELD > 30 s; ROLLING_BACK
non-empty for > 60 s; Greenlight unreachable; reconciliation loop failing.

## 15. Deployment topology

### PoC: single VPS, both roles, signet (Hetzner/DO-class, ~EUR 5/mo)

```
VPS (signet)
|- docker compose
|   |- game-backend  --> postgres/SQLite        # "game producer" role (reference impl)
|   |- escrow service --> CLN (signet) + BoltzExchange/hold
|   |- game-web (static PWA files)
|   `- caddy (automatic Let's Encrypt HTTPS; one domain or DuckDNS subdomain)
`- phones: https://g2c-demo.example.com          # n players, browsers + Zeus(signet)
```

- Players reach only `game-backend` over HTTPS; the DB is never exposed. Escrow and
  game-backend communicate via the section 3.2 contract with HMAC — **keep them
  separate containers even in the PoC**, so the production split is a config change.
- Per-player onboarding: signet faucet coins + one channel Zeus->escrow node.
- Escrow is the product; the demo game doubles as the reference implementation of
  the game-side integration contract (SDK example for game producers).

### Production: roles split

- **Game producer** hosts game-backend + DB on their infra; gives the escrow the API
  base URL + HMAC secret.
- **Escrow (us)** hosts escrow service + CLN node + channel liquidity; the only
  Lightning participant.
- Same code, different `config.yaml` — no redesign between PoC and production.
