# Escrow Service Specification

Item-for-sats escrow over Bitcoin Lightning, coordinated against a third-party game API.
Companion doc: `DISCUSSION_SUMMARY.md` (rationale & decision log).

Status: DRAFT v0.1

---

## 1. Overview

The escrow service is a standalone process that:

1. Issues **hold invoices** to buyers for an item sale.
2. On HTLC lock: instructs the **game backend** to transfer item ownership (idempotent).
3. Pays the **seller** via an invoice resolved from their Lightning address.
4. Settles the hold invoice — completing the buyer's payment — only after 2 and 3
   are confirmed.
5. On any definitive failure before money moved: cancels the invoice (buyer is
   auto-refunded by Lightning's own timeout) and rolls back the transfer if needed.

Guarantee: **no state exists where sats moved and ownership didn't (or vice versa)**,
except recoverable windows documented in §7.

### Components

```
                ┌──────────────┐  HTTPS (HMAC)   ┌───────────────┐
                │ Game backend │◀───────────────▶│ Escrow service │
                │  (3rd party) │                  └───────┬───────┘
                │  items only  │                          │ gRPC (cln-grpc)
                └──────┬───────┘                  ┌───────▼───────┐
                       │ shows payment_request    │ Greenlight    │
                ┌──────▼───────┐  BOLT11          │ hosted CLN    │
                │ Buyer wallet │─────────────────▶│ (our keys)    │
                └──────────────┘                  └───────┬───────┘
                ┌──────────────┐  BOLT11                   │
                │ Seller wallet│◀──────────────────────────┘
                └──────────────┘
```

- **Game backend** (`api.game.example`): owned by third party. Item ownership, user IDs,
  seller Lightning addresses in user profiles. *Holds no sats.*
- **Escrow service** (this spec): Rust or Go or Python; single binary/process; local
  SQLite state store; the only Lightning participant.
- **Greenlight node**: hosted CLN, keys held by us (device credential in secret store).
- **Wallets**: buyer and seller use any wallet (custodial fine). They are never aware of
  the escrow machinery beyond paying a payment request / being paid.

### Explicit non-goals

- No user balance custody of any kind.
- No refunds-as-a-feature: cancellation of the hold invoice is the refund.
- No multi-item/multi-seller carts in v1 (one sale = one item = one hold invoice).
- No on-chain BTC, no other assets.

## 2. Primitives and budget

| Primitive | Source | Notes |
|---|---|---|
| Hold invoice (hash supplied by us, preimage generated by us) | **`BoltzExchange/hold`** CLN plugin on a self-run node — verified 2026-02-14, see `verification-greenlight-holdinvoices.md`. Greenlight: not possible (no plugin support). LND fallback: native `AddHoldInvoice` (requires handing node the preimage at creation — acceptable, weaker than hash-only) | **Milestone 0 outcome recorded; node-backend decision (A/B/C) pending** |
| Invoice status stream | CLN notifications / `listinvoices` polling | drives state machine |
| Seller payout resolution | **PayoutResolver** seam — `LnUrlResolver` (LUD-16) / `NwcResolver` (NWC `make_invoice` via kind 23194/23195) | fresh invoice minted at purchase time; core state machine is resolver-agnostic |
| Payment to seller | CLN `pay` (BOLT11 from PayoutResolver) | `listpays` for status |
| Local transactional state | SQLite WAL | single writer, `payment_hash` as PK |

**Hold window budget**: from HTLC lock to settle must stay well inside the final-hop
CLTV delta. Target: **≤ 10 s** p99 (reserve call + invoice fetch + payment attempt).
Hard alarm at 30 s. Never perform human-in-the-loop actions while holding.

**Invoice expiry**: hold invoice `expiry = 600 s` (unpaid); a paid HTLC carries
`HOLD_CLTV_EXPIRY` (288) blocks of budget. Reaper (§8) cancels unpaid invoices.

**Units**: msat internally everywhere; convert only at edges.

**Fee**: spread. Hold invoice `amount_msat = X`; seller paid `X - fee_msat`.
`fee_msat` configured per sale (default from config, min/max clamps). Fee accrues in
our node's channel balance; periodic sweep/rebalancing is ops concern, out of scope.

## 3. APIs

### 3.1 Escrow API (we serve; called by game backend only, never by game clients)

Auth: HMAC-SHA256 over `(method, path, body, nonce)` with shared per-deployment secret.
Idempotent on `item_id + buyer_id` for in-flight sales (one open sale per item).

```
POST /v1/sales
  { "item_id": "...", "buyer_id": "...", "seller_id": "...",
    "amount_msat": 21000, "fee_msat": 100,
    "seller_payout": { "type": "lnurl", "target": "satoshi@wos.example" }
    // or: { "type": "nwc", "target": "nostr+walletconnect://…" }
    //    (make_invoice-only permission; the URI is a SECRET — encrypt at rest,
    //     never log. Game backend stores payout methods in seller profiles.)
  }
→ 201 { "sale_id": "uuid", "payment_request": "lnbc...",
        "payment_hash": "<hex>", "expires_at": "RFC3339",
        "fee_msat": 100, "seller_amount_msat": 20900 }
        // fee decided by the ESCROW (its revenue), never by the caller

GET /v1/sales/{sale_id}
→ 200 { "state": "HTLC_HELD" | "COMPLETED" | "CANCELLED" | ...,
        "payment_hash": "...", "failure_reason": "..."? }
```

`POST /v1/sales` also takes an optional `fiat_currency` + `fiat_amount`
(`"EUR"`, `"4.99"`): the price as the buyer saw it, recorded so every sale
has its fiat value at the time it was made.

Operator API (`X-Admin-Token`; one token per named person in `ADMIN_TOKENS`,
so the audit trail names who acted; off when unset):

```
GET  /v1/admin/sales/{id}            sale + events + ledger lines (support, disputes)
POST /v1/admin/sales/{id}/resolve    { "note": "..." }  ERROR -> RESOLVED; moves no money
GET  /v1/admin/reports/summary       ?start=&end= (UTC days): outcomes, volume, fees,
                                     routing, losses, net per day; balances; exposure
GET  /v1/admin/reports/ledger.csv    ?start=&end=: every ledger line, with fiat value
GET  /v1/admin/audit/verify          ?events_anchor=&ledger_anchor=: chains + balance check
```

Optional webhook back to game backend on terminal states (separate shared secret).

Both payout types mean the same thing to the core: **a fresh invoice is minted at
purchase time; the seller is never involved at sale time.** Resolution goes through
the internal `PayoutResolver` seam (§2) so the state machine is resolver-agnostic.
Adapter-specific behavior is contained in the adapter: LNURL failures are fast and
unambiguous (HTTP); NWC relay timeouts are ambiguous (wallet offline vs slow) and use
their own deadline before being treated as row #5 failures.

### 3.2 Game API (they serve; called by us; contract to hand to the third party)

Auth: shared secret (`X-Escrow-Secret`). All calls keyed by
`idempotency_key = payment_hash` (hex). **Contractual requirements:** each call is
atomic server-side (one SQL transaction) and replay-safe, and a **reserved item is
frozen**: no trade, listing, drop, craft, consume, mail, delete or admin action may
touch it until it is committed or released.

```
POST /reserve_sale      # freeze the item at the seller for this sale
  { "item_id": "...", "buyer_id": "...", "seller_id": "...",
    "idempotency_key": "<payment_hash>" }
→ 200 { "status": "reserved" | "already_reserved" | "already_committed" }
→ 409 { "status": "rejected", "reason": "item_unavailable" | "sale_released" }
→ 5xx / timeout          # AMBIGUOUS → we retry (idempotent)

POST /commit_sale       # hand the frozen item to the buyer (money is final)
  { "idempotency_key": "<payment_hash>" }
→ 200 { "status": "committed" | "already_committed" }
→ 409 { "status": "rejected", ... }   # unknown/released key: MUST NOT happen
                                      # for a reserved sale (we escalate)

POST /release_sale      # unfreeze; the item never left the seller
  { "idempotency_key": "<payment_hash>", "reason": "..." }
→ 200 { "status": "released" | "already_released" | "not_found_ignored" }
       # not_found: record a tombstone so a late reserve with this key fails
→ 409 { "status": "rejected", "reason": "sale_committed" }

GET /sale_status?key=<payment_hash>
→ 200 { "status": "reserved" | "committed" | "released" | "not_found" }
```

A reservation never expires on the game side by itself: only the escrow releases
it (an auto-expiring reservation could unfreeze an item we are about to commit).
For reconciliation the game asks `GET /v1/sales/{id}` on our side.

### 3.3 Node backend integration — Greenlight ruled out (2026-02-14)

Greenlight cannot load custom plugins (open brainstorm issue #423, "TBD", since
2024-05) and core CLN has no native hold RPCs — so Greenlight offers no path to hold
invoices. Evidence: `verification-greenlight-holdinvoices.md`.

Node backend options:

- **A (recommended): self-run CLN on VPS + `BoltzExchange/hold`** — plugin exposes
  `holdinvoice/settleholdinvoice/cancelholdinvoice/injectinvoice` + gRPC streaming,
  release binaries available; hash-only creation preserves the strong guarantee
  (even the node can't settle without our preimage).
- **B: self-run LND (+neutrino) or LND hoster** — native hold RPCs, spec primitives
  map 1:1; preimage must be supplied at creation.
- **C: ask Blockstream to whitelist the plugin** — pursue in parallel, non-blocking.

Common requirements regardless of option:

- cln-grpc / LND gRPC; node reachable while any sale is in a non-terminal state.
- Notification subscription for invoice state changes (poll as fallback at 1–5 s
  while waiting states exist).
- Credentials (node admin / plugin client certs) from secret manager; never on disk
  in repo.

## 4. Sale state machine

```
AWAITING_PAYMENT ─▶ HTLC_HELD ─▶ RESERVING ─▶ PAYING_SELLER ─▶ SETTLING ─▶ COMMITTING ─▶ COMPLETED
       │                            │              │                │            │
       │ (expired unpaid)           │ (rejected /  │ (payout        │ (buyer     │ (commit
       │                            │  HTLC late)  │  FAILED x N)   │  HTLC lost)│  rejected)
       ▼                            ▼              ▼                ▼            ▼
   CANCELLING ◀──────────────── RELEASING ◀────────┘              ERROR        ERROR
       │                    (release_sale, then cancel)          (LOSS)    (PAID, UNDELIVERED)
       ▼
   CANCELLED
```

State semantics (persisted in SQLite, one row per sale, one driver task per sale):

| State | Meaning | Money moved? | Item |
|---|---|---|---|
| AWAITING_PAYMENT | hold invoice live, payment request returned to game | no | listed |
| HTLC_HELD | buyer's HTLC locked at node | no (held) | listed |
| RESERVING | calling `reserve_sale` (retries); refuses if the HTLC is gone/late | no | → frozen |
| PAYING_SELLER | resolve payout invoice once, pay it; wait while in flight | seller leg | frozen |
| SETTLING | release preimage; buyer's payment completes | yes (all) | frozen |
| COMMITTING | calling `commit_sale`, retried for as long as the game needs | — | → buyer |
| RELEASING | payout definitively failed / never started; `release_sale`, then cancel | no | → unfrozen |
| CANCELLING / CANCELLED | cancel invoice; buyer auto-refunded by protocol | no | seller |
| COMPLETED | seller paid, hold invoice settled, item committed | yes | buyer |
| ERROR | needs a human; `failure_reason` says why (`LOSS:`, `PAID, UNDELIVERED`) | — | frozen |

Invariants:
- **Nothing is undone.** The item moves exactly once (commit), after the money is final.
- **Preimage released ⇔ item reserved AND seller payment confirmed succeeded.**
- **Release/refund only once the seller payment is FAILED or never initiated**
  (in flight ≠ failed); and only after the game confirmed the release.
- **No payout unless the buyer HTLC is still ACCEPTED with `MIN_PAYOUT_CLTV` usable
  blocks; the payout route's timelock is capped below the buyer HTLC's expiry.**
- Commit comes after settle on purpose: commit is a promise on a frozen item, so a
  game outage there only delays delivery; it never puts money at risk.

## 5. Purchase flow (happy path)

```
Game          Escrow                    LND node            Seller wallet
 │ create_sale │                            │                    │
 │────────────▶│ gen preimage+hash          │                    │
 │             │── hold invoice(hash,X) ───▶│                    │
 │◀─ pay_req ──│                            │                    │
 │ (show to buyer)                          │                    │
 │             │◀─ HTLC accepted ───────────│                    │
 │ reserve_sale│ state=RESERVING            │                    │
 │◀────────────│ (retry until 200/409)      │                    │
 │── reserved ▶│ item frozen at seller      │                    │
 │             │ state=PAYING_SELLER        │                    │
 │             │ resolve LN addr → invoice  │                    │
 │             │── pay(X-fee, cltv cap) ───▶│───────────────────▶│
 │             │◀─ pay success ─────────────│                    │
 │             │ state=SETTLING             │                    │
 │             │── settle(preimage) ───────▶│ buyer's pay completes
 │ commit_sale │ state=COMMITTING           │                    │
 │◀────────────│ (retry until 200)          │                    │
 │─ committed ▶│ state=COMPLETED            │                    │
```

## 6. Failure matrix

| # | Failure | Detection | Action | End state | Sats risk |
|---|---|---|---|---|---|
| 1 | Buyer never pays | invoice expiry / reaper | cancel invoice | CANCELLED | none |
| 2 | Buyer pays partially (MPP incomplete) | invoice not fully funded | wait; expiry cancels | CANCELLED | none |
| 3 | `reserve_sale` definitive 409 | response | release (no-op) + cancel | CANCELLED | none |
| 4 | `reserve_sale` timeout/5xx | response/timeout | retry; if the buyer HTLC gets late → release + cancel | RESERVING → … | none |
| 5 | Seller payout resolution fails (LNURL: HTTP error. NWC: relay timeout) | resolver result | retry N; then release + cancel | RELEASING → CANCELLED | none |
| 6 | Seller payment routing fails | node reports FAILED | retry same invoice N; then release + cancel | RELEASING → CANCELLED | none |
| 6b | Seller payment stuck in flight | node reports IN_FLIGHT | **wait**; never release while in flight | PAYING_SELLER → … | none (route timelock capped below buyer HTLC) |
| 7 | Seller paid, settle fails | node error + invoice lookup | retry; if the invoice is CANCELED → ERROR `LOSS:` | SETTLING → COMMITTING / ERROR | **principal loss only if the buyer HTLC was lost; alert + manual reconcile** |
| 8 | `commit_sale` timeout/5xx | response/timeout | retry forever (money is final, item frozen) | COMMITTING → COMPLETED | none |
| 9 | `commit_sale` 409 (game lost the reservation) | response | ERROR `PAID, UNDELIVERED` | ERROR | none for us; buyer needs delivery or refund by hand |
| 10 | `release_sale` 409 (game says committed) | response | ERROR, no refund | ERROR | manual |
| 11 | Crash anywhere | restart | §8 reconciliation | — | none beyond #7 |

## 7. Trust & atomicity statement (for the third party)

The cross-system commit points, in order: (a) `reserve_sale` confirmation (item
frozen), (b) seller payment success, (c) preimage release (buyer's payment final),
(d) `commit_sale`. The item changes owner only at (d), after the money is final, so
the game never has to undo a transfer. The game's idempotency on `payment_hash` and
its enforcement of the freeze are what make the design hold; without them it is void.

## 8. Crash recovery & reconciliation

Every loop tick (0.5 s):

1. Load all sales in non-terminal states; drive each in its own task.
2. Ask the node: hold invoice state + blocks left, seller payment state by hash
   (TrackPaymentV2). An unreachable node means "decide nothing", never "not paid".
3. Drive the state machine forward per §4 invariants; all game calls are idempotent
   (`payment_hash` keys everywhere), so a crash between any two steps just repeats
   the last call.
4. Retry pending game webhooks (terminal states) with backoff.

Reaper: sales in AWAITING_PAYMENT past `expires_at + 60 s` → cancel invoice, CANCELLED.

## 9. Local store (SQLite)

One file, three tables (`escrow/app.py`, `escrow/ledger.py`). Every state
change writes all of its rows in ONE transaction.

- **`sales`**: the work queue. One mutable row per sale: current state, the
  next action's inputs (payout invoice and hash, attempts, pending game
  webhook), amounts, the optional fiat price the buyer saw, and the actual
  routing fee once paid. Personal data lives only here: the payout target
  is erased when a sale ends COMPLETED, CANCELLED or RESOLVED (an ERROR sale
  keeps it for the human who handles it). Player ids are the studio's
  pseudonyms; erasing the person behind them is the studio's side.
- **`sale_events`**: append-only audit trail. One row per transition: time
  (UTC), from, to, reason, actor (`system`, `api`, or `operator:<name>`),
  and JSON facts (amounts, hashes; the preimage once settled, as proof of
  payment; never personal data).
- **`ledger`**: append-only double-entry ledger, in msat, debit positive.
  Each journal entry sums to zero and is booked at most once.

  | Entry | When | Lines |
  | --- | --- | --- |
  | `<sale>:seller_paid` | payout confirmed | clearing:sales +seller, expense:routing +fee, assets:lightning −both |
  | `<sale>:buyer_settled` | buyer HTLC settled | assets:lightning +amount, clearing:sales −seller, revenue:fees −fee |
  | `<sale>:loss` | LOSS error | expense:losses +seller, clearing:sales −seller |

  `clearing:sales` is what g2c has fronted and not yet collected: the live
  exposure.

Both append-only tables refuse UPDATE and DELETE (triggers) and are
hash-chained (each row hashes the previous row's hash plus its own fields).
`GET /v1/admin/audit/verify` recomputes the chains and checks that every
entry balances; its `heads` are copied off-site daily and passed back as
anchors, so a rewritten tail is detected too.

Not yet: the preimage is stored in plain text (encrypt at rest, or adopt
same-preimage chaining so g2c never creates one), no schema migrations
(an older file is refused at startup), no Postgres.

## 10. Security

- Escrow API & Game API: HMAC-SHA256, nonce + timestamp window (±30 s), constant-time
  compare.
- Preimages encrypted at rest (AES-GCM, key from secret manager / env).
- Greenlight device credential in secret manager; no macaroons on disk.
- The escrow process holds power equivalent to "transfer items without payment" toward
  the game — treat the HMAC link as production-critical, rotate secrets, IP allowlist.
- Logs: never log full preimage or payment_request beyond operational need; hash-prefix
  correlation IDs instead.

## 11. Observability

Metrics (Prometheus): sales by state, hold-window duration histogram, game API
latency/error rate, seller payment failure rate, count in SETTLING (must be ~0),
count in RELEASING / COMMITTING, count in ERROR (must be 0), fee earned (msat).

Alerts: any sale in ERROR; any sale in SETTLING > 5 s; any sale in HTLC_HELD or
RESERVING > 30 s; COMMITTING > 60 s (game down, item frozen, buyer waiting);
node unreachable; reconciliation loop failing.

## 15. Deployment topology

### PoC: single VPS, both roles, signet (Hetzner/DO-class, ~EUR 5/mo)

```
VPS (signet)
|- docker compose
|   |- game-backend  --> postgres/SQLite        # "game producer" role (reference impl)
|   |- escrow service --> CLN (signet) + BoltzExchange/hold
|   |- game-web (static PWA files)
|   `- caddy (automatic Let's Encrypt HTTPS; one domain or DuckDNS subdomain)
`- phones: https://g2c-demo.example.com          # n players, browsers + Zeus(signet)
```

- Players reach only `game-backend` over HTTPS; the DB is never exposed. Escrow and
  game-backend communicate via the section 3.2 contract with HMAC — **keep them
  separate containers even in the PoC**, so the production split is a config change.
- Per-player onboarding: signet faucet coins + one channel Zeus->escrow node.
- Escrow is the product; the demo game doubles as the reference implementation of
  the game-side integration contract (SDK example for game producers).

### Production: roles split

- **Game producer** hosts game-backend + DB on their infra; gives the escrow the API
  base URL + HMAC secret.
- **Escrow (us)** hosts escrow service + CLN node + channel liquidity; the only
  Lightning participant.
- Same code, different `config.yaml` — no redesign between PoC and production.
