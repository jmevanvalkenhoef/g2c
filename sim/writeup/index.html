What it takes to run a Lightning escrow

G2C lets players trade in-game items for bitcoin with one guarantee: the item and the money move together, or neither moves. Before running it for real money, I wanted to know what running it would take: how much money it pays out before it collects, which fee it needs, how often a buyer gets a refund and when an operator should be woken up. I ran the escrow's own state machine through – simulated weeks in which the network, the node and the game fail at random, each week under four fee structures.

The escrow

A trade runs through four steps in a fixed order, from the easiest to undo to the hardest. When the buyer pays, the payment is locked at G2C's Lightning node: G2C can claim it or give it back, and only G2C holds the secret that claims it. Then the game reserves the item, which freezes it at the seller. Then G2C pays the seller, claims the buyer's payment, and the game hands the item to the buyer.

The code follows four rules, each of which closes a way to pay the seller and refund the buyer as well. It never refunds while the seller's payment might still land, and "timed out" does not count as "failed". It only pays the seller while the buyer's locked payment has enough time left. After an error on settling, it asks the node what happened instead of guessing. And it releases the item before it refunds the buyer. Every step can be repeated safely, so after a crash the escrow simply carries on from the state it saved.

An earlier version of this contract has completed one real sale on the Bitcoin mainnet. Everything below is about what it would take to run the current version every day.

What is real and what is simulated

The simulation runs the escrow's own state machine, unchanged, and lets it write its own database. Everything around it is simulated.

The telemetry is read from the database with the queries a dashboard for the live service would use: sales per hour, money per day, sales that need a person, money fronted and stuck sales. The simulated world

None of the rates is measured; there is no traffic yet to measure them from. Each is an assumption with a range, and every simulated week draws its own values from those ranges, so a conclusion only counts when it holds across them. The model is hierarchical: the ranges set one week's rates, the rates set how often things go wrong at each moment, and each sale and each call then succeeds or fails.

Traffic follows a daily rhythm with an evening peak and busier weekends. Prices have a long tail of rare, valuable items, and large payouts fail more often than small ones, as they do on Lightning when a route runs short of liquidity. Routing costs about one sat plus 0.05% of the amount, and the escrow refuses any route that costs more than the sale's own fee.

Faults do not arrive one at a time. Each week alternates between healthy periods of a day or two and bad periods of about half an hour in which every fault rate is several times higher, the way a network has bad hours. Outages of the node and the game come on top, and a few of them last twenty times longer than usual. The faults that test the escrow hardest are lost answers: the node pays the seller, or the game reserves the item, and the escrow never hears back. After each week the faults stop and every open sale gets six hours to finish.

Checking the checker

After each week, every sale is compared with what really happened in the simulated world, not with what the escrow believes. A completed sale must have a settled buyer payment, exactly one seller payment and an item with the buyer. A cancelled sale must have no seller payment and the item back with the seller. A sale that needs a person must be one the rules allow for. The ledger's hash chains must be intact, and no sale may still be open at the end.

To see whether these checks would notice a broken escrow, I broke it twice on purpose, without touching its code. In the first version, the escrow forgets to ask whether the seller was paid before it refunds the buyer. In the second, it forgets the seller's invoice after a lost answer and pays the seller again with a new one. Over five simulated three-day periods, the checks reported 43 broken sales for the first and 304 for the second, including sellers paid twice. The escrow as it is reported none.

Money paid out before it comes in

G2C pays the seller before it collects from the buyer. The buyer's payment is already at G2C's node by then, but it is locked, and G2C claims it only after the payout to the seller has gone through. That order is what lets a failed payout end in an automatic refund. A locked payment can't be spent, so the seller is paid from G2C's own balance on its channels, and for a moment G2C has paid without having collected. That moment is booked in the ledger as money fronted.

What matters most

Each world drew its own assumptions, so across the – worlds the rank correlation between an assumption and an outcome shows which assumptions decide it. With 50 worlds, correlations below about 0.3 are within noise.

Refunds come mostly from the game. Items the game refuses to reserve correlate – with the refund rate, against – for failed payouts. Time with stuck sales follows payouts that get stuck (–), and profit follows what routing costs per sat moved (–). The peak fronted follows the price of the largest items, as the first chart shows.

That sets what to measure first once G2C is live: how often the game refuses an item, and how often seller payouts get stuck. Together they decide most of what buyers and operators will see. The telemetry queries in this simulation already measure both.

Limits

  • The world is assumed. Every rate is a stated assumption with a range. The conclusions hold across those ranges, not beyond them.
  • The Lightning network is not simulated. The simulated node behaves the way I expect a real one to; a real node can surprise in ways this model cannot.
  • Routing is one number per payout. A payout to a seller passes through other nodes, usually large hubs, and each charges a fee. The simulation draws the total of those fees per payout, around one sat plus 0.05% with a wide range per week, and does not model the hops themselves. The floor of about 0.5% for the fee depends directly on that assumption. The cost of G2C's own channels is left out too: opening them, buying inbound liquidity and rebalancing them as payments flow.
  • Buyers do not react to the fee. A higher fee in the simulation earns more without losing sales, which a real market would not allow.
  • Prices are assumed too. The money fronted is set by the largest sales, so it is only as right as the assumed tail of rare, valuable items.
  • One escrow process, one node. The service as built runs one process on one node; scaling beyond that is outside this simulation.

Reproduce it

# the checks catch both broken escrows
cd escrow
uv run python ../sim/mutants.py
# the simulated weeks, about an hour on four cores
uv run python ../sim/run.py --worlds 50 --days 7 \
    --fees 1000:10000,1000:5000,0:15000,5000:5000 --jobs 4
# summary.json and the charts' data.json
cd .. && uv run sim/analyze.py
